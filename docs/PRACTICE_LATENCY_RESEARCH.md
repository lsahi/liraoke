# 练歌房监听延迟调研简报

日期：2026-10-30。结论：保留练歌房初版，暂不合入延迟实验。

## 已完成的对照

- 初版为独立练歌房窗口，使用当前工程媒体和字幕，实时监听但不保存录音；与 AI 功能独立。
- 用户最初反馈约 150 ms 延迟；一轮缓冲/RAW 等调整后反馈约 350 ms，已回退。这些数字是用户体验或自行测量反馈，没有统一的声学往返测量条件。
- 临时分支学习 Performous 的缓冲监控和动态同步：模拟时钟漂移测试显示可减少长期积压，但用户听感不如初版，因此不采用。
- 关闭后台游戏没有明显变化；VT-3 换成摄像头 USB 麦克风后听感基本一致。尚无证据把游戏或 VT-3 特有处理认定为主要原因。
- 独立最小诊断程序移除歌曲混音、视频、歌词和 AI，仍保留相同 WASAPI/NAudio、缓冲及必要的采样率转换；用户反馈与初版相近。
- 用户测试其他 K 歌软件，也感到延迟，估计约 80–120 ms；没有统一实测，不能当作本机硬件下限。

## 共享 / 独占模式

设备：1080P USB Camera-Audio → Realtek USB Audio 耳机。摄像头输入 16 kHz 单声道，应用输出 48 kHz 双声道。

| 模式 | 输入 / 输出 | 用户反馈 |
| --- | --- | --- |
| A | 共享事件 / 共享事件 | 延迟明显，感觉超过 150 ms |
| B | 共享事件 / 独占事件 | 比 A 略好 |
| C | 独占轮询 / 共享事件 | 与 A 无明显差别 |
| D | 独占轮询 / 独占事件 | 与 B 无明显差别 |

用户提供的 A 样本持续 16.9 秒：队列当前/峰值 0/10 ms，累计补零 54.25 ms，积压丢弃 0 次；B 持续 12.3 秒：队列当前/峰值 20/20 ms，累计补零 50.19 ms，积压丢弃 0 次。

解释与限制：

- 短时统计未显示持续积压。累计补零不是每段声音附加的固定延迟；队列深度、库报告周期均不是完整耳返延迟。
- B 队列更大但听感略好，因此不能根据队列数字直接排序听感。
- 四组均请求 20 ms；共享路径库报告 10 ms，独占路径 20 ms。独占输入使用轮询，且输入/输出位深可能从浮点改为 PCM。不是所有条件完全相同的严格实验。
- 输出路径值得优先调查，但输入端固有延迟仍不能排除。尚未定位主要延迟来源，也没有证明任何实验稳定降低了声学往返延迟。

## 开源参考与暂缓方案

- [Performous](https://github.com/performous/performous/blob/e300578334beb6c81789de08b95e0a7dfaf70b66/game/analyzer.cc#L32-L60)：按队列深度微调消耗速度，积压过大时丢弃旧音频，主要控制跨设备时钟漂移。我们的实验独立实现，没有复制其源码。
- [Vocaluxe](https://github.com/Vocaluxe/Vocaluxe/blob/5767914372940b2f75e8dd0982b0d839ffb0fcc8/Vocaluxe/Lib/Sound/Record/CBuffer.cs#L89-L98)：所检查路径主要做音准分析，人声回放代码被注释；其延迟测试不能等同于实时耳返降延迟方案。
- 伴奏/人声混响仅作为未来听感选项，不视为延迟修复，本轮未实现。
